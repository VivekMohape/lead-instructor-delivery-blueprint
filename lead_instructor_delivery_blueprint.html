DELIVERY SYSTEM/Lead Instructor Blueprint
Executive delivery blueprint for Thimphu, Bhutan

Build real capability.
Show the evidence.

A practical delivery plan for a three week, on site program in autonomous agentic AI and the Model Context Protocol. It is designed for experienced engineers, with a focus on production practice, demonstrated skills and a clear handover to the GovTech PMO.

01 · Intended outcomes

Measure what people can do.

Each outcome should lead to something a participant can build, demonstrate, test or explain without relying on a teammate.

Definition of success
01 BUILD

Working systems

Participants deliver a Streamlit application with an agentic workflow, custom MCP integration, controlled data access and containerized components.

02 SECURE

Enforced controls

Access boundaries, database permissions, execution limits, human approval paths and failure handling are demonstrated by tests, not only described.

03 VERIFY

Individual evidence

Baseline, daily milestone and final assessments show what each participant can independently implement, troubleshoot and explain.

02 · Operating model

Six workstreams, one delivery plan.

The program moves from requirements and setup through teaching, validation, assessment and handover.

Ownership from planning through handover
Workstream 01Before the program

Discover & align

Confirm client outcomes, participant profile, approved curriculum, cloud constraints, data rules, staffing and acceptance criteria.

↗ Output: approved delivery brief
Workstream 02Before the program + Day 1

Assess & customize

Baseline skills in Python, Git, APIs, databases, cloud, containers and AI. Adjust pacing without weakening required learning outcomes.

↗ Output: cohort map and lab plan
Workstream 03Before Day 1

Provision & validate

Prepare isolated team environments, repositories, Docker services, approved model endpoints, database access, quotas and diagnostics.

↗ Output: verified readiness register
Workstream 04Days 1 to 12

Build & mentor

Use the eight hour daily cycle, code reviews, milestone checkpoints and a shared issue log to keep all teams progressing.

↗ Output: tested working increments
Workstream 05Days 13 to 15

Hackathon & evaluate

Facilitate scoped project delivery, technical troubleshooting, security checks, latency measurement and live demonstrations.

↗ Output: demos and scored evidence
Workstream 06Closeout

Assess & hand over

Consolidate individual competency results, project evidence, development gaps and recommendations for GovTech project matching.

↗ Output: Skills Registry and handover

The curriculum moves from foundations to integration, production controls and final demonstration. Expand any day to review its activities and expected evidence.

02Day

Streamlit and collaborative Git

Build the interface and establish reviewable team engineering practices.

StreamlitGit branchingCode review
Concept + demo

Application structure, feature branches, pull requests, conflict resolution, tests and branch protection where supported.

Practical + mentored build

Participants implement separate UI features, open pull requests, review a peer's change and resolve a controlled merge conflict.

Evidence collected

Feature branches, reviewed pull request, successful integration and test output.

03Day

Agentic AI architecture and LangGraph

Introduce state, routing, tool use and controlled termination.

Agent designStateWorkflow
Concept + demo

Compare deterministic workflows and agentic loops. Explain graph state, node responsibilities, conditional transitions, tool invocation and stop conditions. Discuss framework tradeoffs across LangChain, LlamaIndex and LangGraph; use the framework approved by GovTech for the reference build.

Practical + mentored build

Implement a small graph with a tool call and validation step. Add error handling and a bounded iteration policy.

Evidence collected

Running workflow, state schema and test cases for valid, invalid and incomplete results.

Instructor focus

Challenge unnecessary agent complexity and make every transition observable.

Definition of done: workflow runs end to end and exits predictably under tested conditions.
⌄
04Day

Multi agent coordination and evaluation

Introduce task decomposition, validation, retries and failure recovery.

Multi agentTestingEvaluation
Concept + demo

Agent responsibilities, shared state, coordination patterns, bounded retries, output validation and when a single workflow is preferable.

Practical + mentored build

Extend the workflow with a specialized component and verifier. Test a failed tool response and malformed output.

Evidence collected

Workflow traces, validation tests, evidence of failure handling and a short architecture explanation.

Instructor focus

Assess whether the additional agent improves quality enough to justify added latency and complexity.

Definition of done: each agent or node has a clear responsibility and the result is validated before returning.
⌄
05Day

Custom MCP server fundamentals

Build a server with explicit tools, schemas and predictable responses.

MCPTool schemasProtocol testing
Concept + demo

Host, client and server roles; tool discovery and invocation; capability contracts; selected SDK and transport, based on client requirements.

Practical + mentored build

Implement a small MCP server exposing a clearly defined tool; validate its arguments and invoke it through an approved client.

Evidence collected

Server source, input schema, a successful tool call and basic error tests.

Instructor focus

Ensure participants can explain the boundary between model requests and trusted authorization enforced by the server.

Definition of done: client discovers and invokes an MCP tool, and malformed inputs are handled safely.
⌄
06Day

MCP integration and error handling

Make tool interfaces predictable and resilient to dependency failures.

MCPTimeoutsIntegration tests
Concept + demo

Tool contracts, error classification, timeouts, bounded retry behavior, client compatibility and diagnostics.

Practical + mentored build

Test invalid inputs, unavailable APIs and controlled failures. Improve output validation and logging.

Evidence collected

Integration tests, error behavior and a documented failure recovery path.

Instructor focus

Prevent silent failures and fabricated success; make tool results easy to inspect.

Definition of done: errors are explicit, bounded and diagnosable; expected failures are covered by tests.
⌄
07Day

Secure database integration

Expose approved database operations through a controlled gateway.

Database gatewayLeast privilegeSQL safety
Concept + demo

Database gateway patterns, parameterized queries, permissions based on roles, data minimization, auditing and separation of model intent from trusted execution.

Practical + mentored build

Build an MCP tool for an approved query; test valid, malformed and unauthorized requests against the training dataset.

Evidence collected

Permission configuration, successful query, denied operation and database audit evidence where available.

Instructor focus

Do not expose unrestricted SQL or broad database credentials to the agent.

Definition of done: allowed queries succeed and unauthorized operations are blocked by trusted code or database policy.
⌄
08Day

Agent containment and human override

Enforce tool boundaries, safe execution and approval for sensitive actions.

Threat modelingApproval flowAudit
Concept + demo

Prompt injection, untrusted outputs, tool authorization, runtime limits and human confirmation for high impact actions.

Practical + mentored build

Implement a permission check and approval or rejection step; attempt a prohibited call and verify it is denied.

Evidence collected

Negative tests, audit events, demonstrated override and documented threat assumptions.

Instructor focus

Enforce security in application and infrastructure layers, not solely through prompt instructions.

Definition of done: a defined sensitive action can be paused, approved, rejected or stopped, and unauthorized requests are denied.
⌄
09Day

Docker and containerization

Make the application reproducible and operationally inspectable.

DockerNetworkingHealth checks
Concept + demo

Image construction, environment configuration, networking, health checks, execution without root privileges and safe secret handling.

Practical + mentored build

Containerize app and MCP service, run them together and diagnose a controlled network or startup failure.

Evidence collected

Build logs, container health, startup instructions and a reproducible local run.

Instructor focus

Verify behavior from a clean checkout rather than a developer's preconfigured machine.

Definition of done: another participant can build and run the services using documented configuration.
⌄
10Day

Practical + mentored build

Instructor focus

Use the client's selected cloud and existing security controls; avoid unnecessary parallel infrastructure.

Definition of done: approved components deploy and run in the designated environment with intended permissions.
⌄
11Day

Production MLOps and observability

Establish testing, release discipline, logs, traces and performance baselines.

Test strategy, repeatable builds, versioned configuration, monitoring, tracing and rollback concepts.

Practical + mentored build

Run the test suite, inspect an agent trace and measure an agreed latency metric. Identify the main bottleneck.

Test results, operational logs, measurement method and deployment/recovery notes.

Instructor focus

Definition of done: team can test its release, inspect a failed request and explain its measured performance.

DELIVERY MODALITY · OPTION 1

The five day intensive alternative.

A five day intensive sprint can work for a cohort with strong foundations and a preconfigured environment. It is a compressed alternative, not a like for like replacement for the full 15 day residency.

Compressed format · narrower scope

Day 2Intensive agentic workflow and custom MCP integration; secure database pattern; container/cloud deployment walkthrough and security gates.Working vertical slice with a defined MCP tool and approved data interaction.Preconfigured templates and cloud environment; limited scope.
Day 3Hackathon kickoff, design checkpoint, implementation of core functionality.Runnable end to end baseline and task ownership.Challenge brief and acceptance criteria approved in advance.

Scope tradeoff

Protect the final three days for the hackathon.

In this option, the first two days prepare teams for a three day hackathon. This is feasible only with strong Python and Git fundamentals, preconfigured environments, a tightly scoped challenge and reduced learning outcomes. Agree the contact hours, support model and assessment depth before committing to this format.

06 · Competency evaluation

Assess demonstrated skills.

This proposed rubric uses observable evidence: demonstrations, tests, code reviews and each participant’s own explanation, rather than attendance alone.

Proposed scoring model
DimensionWeightEvidence to look for
Agentic workflow correctness15%Intended workflow executes; state transitions, validation, stopping conditions and failure branches are understood.
MCP implementation15%Tool schemas are explicit; authorized calls work; input errors and dependency failures are handled predictably.
Secure database integration20%Approved operations work through a controlled gateway; least privilege and negative tests are demonstrated.
Containment and security20%Tool permissions and execution boundaries are enforced; sensitive actions follow the required approval policy.
Reliability and MLOps10%Repeatable tests, versioned changes, logs, failure handling and deployment/recovery steps are shown.
Latency and operations10%Measurement method is explained; traces identify meaningful sources of latency and resource use.
Human override10%Required sensitive actions can be paused, approved, rejected or stopped, with the decision traceable.
Proposed total weighted score100%
Critical security gates

Some failures should block approval.

Weighted scoring should not conceal a critical security defect. Agree pass/fail gates and remediation policy with the client before training.

08 · Delivery risk management

Resolve risks before they block delivery.

Open a risk to review its proposed response. Assign an owner and due date during kickoff.

Proposed register
Cloud access, credits or quotas are not readyHigh impact⌄
Impact: Day 1 is consumed by setup; teams cannot complete labs.
Mitigation: Set a readiness deadline before the program starts, test access for each participant, confirm budget ownership and prepare an approved fallback for noncritical dependencies.
Unauthorized execution or database accessCritical risk⌄
Impact: Data exposure, unwanted changes or breach of the agreed sandbox boundary.
Mitigation: Least privilege, controlled database gateway, restricted runtime, network controls, resource limits, negative tests and human approval for designated actions.
Uneven participant experienceDelivery⌄
Impact: Some participants fall behind while advanced participants wait.
Mitigation: Baseline assessment, balanced groups, individual rotations, additional challenge tasks and competency tracking that prevents one person from doing all the work.
External API or MCP integration becomes unreliableDependency⌄
Impact: Labs or hackathon teams become blocked by a dependency outside their control.
Mitigation: Pretest reference integrations, apply bounded timeouts/retries, expose clear errors and prepare approved mocks for noncritical dependencies.
Hackathon scope exceeds available timeSchedule⌄
Impact: Teams reach the final demo without a working vertical slice.
Mitigation: Approve a minimum viable outcome, establish daily checkpoints, assign roles and defer nonessential features until core functionality works.
Inconsistent competency scoringGovernance⌄
Impact: Skills Registry does not provide reliable evidence for project matching.
Mitigation: Agree the rubric in advance, calibrate assessors using sample work, collect observable evidence and distinguish individual ability from team outcomes.
Critical dependencies have no clear ownerGovernance⌄
Impact: Access, security or operational blockers remain unresolved during delivery.
Mitigation: Assign an owner and escalation path for cloud access, security approvals, logistics and technical support before kickoff.
Attendance records or training modality are not agreedCompliance⌄
Impact: Physical attendance or delivery hour requirements cannot be evidenced at handover.
Mitigation: Agree the official on site check in method, daily reconciliation owner, exception handling and record retention; document which modality is authorized before the schedule is issued.
